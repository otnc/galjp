# galjp v5 詳細設計書

| 項目           | 内容                      |
| -------------- | ------------------------- |
| 対象バージョン | `galjp@5.0.0`             |
| 現行バージョン | `galjp@4.0.0`             |
| ステータス     | Draft（実装前レビュー用） |
| 最終更新       | 2026-07-31                |

### 前提（v4 からの方針転換）

1. **v4 との後方互換は考慮しない。** 出力・API とも自由に変更する。
2. **語句単位の特殊変換（`lib/word.json`）は廃止する。**
3. **ひらがな・カタカナの変換表は v4 のまま維持する。** 1:1 対応を変えない。
4. **漢字は全面的に作り直す。既存の変換結果は 1 字も保存しない。**
   `lib/chars/kanji.json` は**設計の参考資料**として扱い、成果物には一切引き継がない。

前提 4 により、v4 の漢字データは「制約」ではなく「観察対象」になる。
本書で v4 データを引用しているのは、**設計方針が人手による判断を再現できることの
裏付け**としてであり、出力を一致させる目的ではない。

## 0. サマリ

本設計の対象は事実上 **漢字レイヤのみ**である。かな・英数・記号は v4 の表をそのまま移植し、
語句レイヤは廃止する。

v4 の漢字処理は「変換結果」を 4,768 行のテーブルに手書きで持っている。
v5 ではこれを **「構造（どこで分割するか）」×「スタイル（部品をどう書くか）」** に分離し、
さらに **異体字置換**という新しい変換経路を追加する。

実データの調査により、v4 の漢字テーブル 87KB は次の 3 つに還元できることを確認した。

| 構成要素                       | 件数     | 説明                                                        |
| ------------------------------ | -------- | ----------------------------------------------------------- |
| 構造テーブル                   | 約 3,350 | `信 = ⿰亻言` のような偏旁分割（IDS 相当）                  |
| コンポーネント・スタイルマップ | **44**   | `亻→ｲ`, `氵→ｼ`, `口→ﾛ` … 手書きで維持する唯一の“センス”部分 |
| 同形置換テーブル               | 13       | `上→㊤`, `亜→亞` など分解ではない置換                       |

つまり **v4 が 4,768 行かけて表現していたものは、実質 57 件の判断に還元できる**。
v5 ではこの 57 件を**出発点に新規設計し**（v4 の値は引き継がず、拡充して約 80 件とする）、構造テーブルは KanjiVG から、
異体字テーブルは Unicode Unihan から、いずれもビルド時に生成する。

前提 4（既存の変換結果を保存しない）により、v4 が採れなかった選択肢が 3 つ開く。

| #   | v5 で解禁されること                                  | 効果                                                                                    |
| --- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 1   | **上下分割（`⿱`）をトップレベルでも許可**（§6.3.1） | `男→田ｶ` `早→日十` `花→ﾅﾅ化`。v4 で未変換だった 1,409 字の大半に経路ができる            |
| 2   | **部品スタイルの拡充**（§5.5）                       | v4 は 44 部品しか装飾していなかった。`⺮→ｹｹ` `宀→ウ` `艹→ﾅﾅ` などを足すと全字に波及する |
| 3   | **単体部品字の装飾**（§6.1 経路 5）                  | `口→ﾛ` `力→ｶ` `又→ﾇ`。v4 では分解できない 1 部品字は絶対に変換されなかった              |

|                            | v4                                     | v5（目標・要計測）                     |
| -------------------------- | -------------------------------------- | -------------------------------------- |
| 手書きデータ行数           | 4,768                                  | **約 80**（44 → 拡充後 60〜70 + 例外） |
| 変換できる漢字             | 3,359                                  | **8,000 以上**                         |
| 収録字のうち変換できる割合 | **70.4%**（4,768 字中 3,359 字。実測） | **77.7%**（JIS X 0208・§15.1 実測）    |
| 変換経路                   | 分解のみ                               | 分解 + 異体字 + 同形置換 + 単体装飾    |
| `亻` の見た目を変える作業  | 202 行を編集                           | **1 行**                               |

> v5 側の数値はいずれも目標であり、フェーズ 4 完了時に `scripts/coverage.ts` で実測する（§7.3）。

あわせて TypeScript 化、ESM/CJS デュアル出力、ランタイム非依存（Web 標準のみ）を行う。

### 1.3 v4 の問題点

#### (a) レイヤ間のカスケード汚染

各テーブルを `if` で順に適用しているため、前段の出力が後段の入力になってしまう。

```js
if (booleans.alphabet && alphabet[c.toUpperCase()]) c = alphabet[c.toUpperCase()];
if (booleans.kata && kata[c]) c = kata[c]; // ← 直前の出力を再度変換
```

実測:

```
'E' → alphabet で 'ヨ' → katakana で '∋'   （'ヨ' はカタカナ表に存在する）
```

このため README の記載と実際の出力が食い違っている。

| README の記載          | 実際の出力            |
| ---------------------- | --------------------- |
| `丩ヨ└└口 山口尺└囙.ᐟ` | `丩∋└└口 山口尺└囙.ᐟ` |

**かな表を維持する以上、この不具合の修正は必須**（`ヨ` `ｦ` などが英数の出力と衝突するため）。

#### (b) 部品表記のゆれ

「結果」を直接書いているため、同じ部品が別表記になっても検出できない。

```
郎 → 良⻏   郡 → 君⻏   都 → 者⻏   郊 → 交⻏     （正しい ⻏）
部 → 立ﾛ卩                                       （誤り。卩 は別部品）
```

`卩` は `叩→ﾛ卩` `即→艮卩` `却→去卩` など 12 箇所で正当に使われているため、
単純な検索では発見しにくい。構造とスタイルを分離していれば起こり得ない不整合。

#### (c) 再帰の展開結果が焼き込まれている

部品として使われている 969 種のうち 645 種はテーブルのキーにも存在するが、
そのうち値が非空なのは 37 種のみ。つまり `例→ｲ歹ﾘ`（`例=⿰亻列`, `列=⿰歹刂`）のような
2 段分解は**あらかじめ手で展開した結果**が保存されている。
`列` の分解を変えても `例` `烈` `裂` には反映されない。

#### (d) その他

| 問題                 | 内容                                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| 空文字列で例外       | `generate('')` が `input must be string.` を throw する（`!input` 判定）                            |
| サロゲートペア非対応 | `text.split('')` が UTF-16 コードユニット分割。BMP 外の漢字をキーにできない                         |
| ランタイム制約       | 関数本体で `require()` を呼んでおり、ブラウザ / Deno / Workers で動作しない                         |
| 保護領域なし         | URL やコードが無差別に変換される（`https://example.com/A` → `丩ＴＴ尸丂://∋乂∀人人尸└∋.⊂口人人/∀`） |
| 型定義なし           | `.d.ts` を同梱していない                                                                            |
| テストなし           | `npm test` が `exit 1`                                                                              |

### 1.4 語句レイヤ（`word.json`）を廃止する理由

```json
{ "まじ": "маＵ”", "てゆうか": "〃ﾉ塚", "愛してる": "愛ιτゑ", "仲良し": "ｲ㊥ょＵ", "チート": "升" }
```

5 件を文字レイヤ単体の結果と突き合わせると、性質が 2 つに割れる。

| 語句       | 語句レイヤ | 文字レイヤ単体 |                                              |
| ---------- | ---------- | -------------- | -------------------------------------------- |
| `まじ`     | `маＵ”`    | `маＵ”`        | **完全に冗長**                               |
| `愛してる` | `愛ιτゑ`   | `愛Ｕτゑ`      | `し` が `ι`（かな表は `Ｕ`）**表記が不整合** |
| `仲良し`   | `ｲ㊥ょＵ`  | `ｲ中良Ｕ`      | `良→ょ` は語呂合わせ                         |
| `てゆうか` | `〃ﾉ塚`    | `τゅכֿｶゝ`     | 「つーか」への言い換え                       |
| `チート`   | `升`       | `千→├`         | 「ます」への語呂合わせ                       |

| 理由                         | 内容                                                                                            |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| **1 件は完全に冗長**         | `まじ` は文字レイヤだけで同じ結果になる                                                         |
| **残り 4 件は表記が不整合**  | `愛してる` の `し→ι` はかな表の `し→Ｕ` と食い違う。同じ文字が文脈で別表記になる                |
| **収録基準が無い**           | 残りは語呂合わせ・言い換えであり、なぜこの 4 語だけなのかを説明できず、増やす方針も立たない     |
| **出力が再変換される**       | `仲良し → ｲ㊥ょＵ` の `ょ` は語句レイヤの出力なのに、後段のひらがなレイヤの走査対象になっている |
| **順序が不定**               | `Object.keys()` の列挙順に依存するため、辞書が増えると優先順位が決まらない                      |
| **正規表現インジェクション** | `new RegExp(word, 'g')` にキーをそのまま渡している。ユーザー辞書を受け付ける拡張で破綻する      |

語句単位の置換が必要になった場合は、§8.2 の `dictionary` オプション
（ユーザーが明示的に渡す最優先ルール）で代替する。標準辞書としては同梱しない。

## 2. 目標 / 非目標

### 2.1 目標

1. **G1 — 保守性**: 漢字の見た目を変える作業を「1 箇所の編集」で完結させる。
   `亻→ｲ` の変更が 202 字へ自動反映されること。
2. **G2 — 網羅性**: 手書きデータを増やさずに変換できる漢字を増やす。
   構造・異体字データを外部ソースからビルド時に取り込む。
3. **G3 — ランタイム非依存**: Web 標準 API のみで動作する。
   ブラウザ / Node.js / Deno / Bun / Cloudflare Workers で同一コード。
4. **G4 — 型安全**: TypeScript で記述し、型定義を同梱する。
5. **G5 — 正しさ**: §1.3 の問題をすべて解消する。
6. **G6 — かなの保存**: ひらがな・カタカナ・英数・記号の変換結果を v4 から変えない。
   **漢字はこの対象外**（前提 4）。

### 2.2 非目標

- **v4 との出力互換・API 互換**（明示的に破棄する）
- **v4 の漢字変換結果の保存**（前提 4。1 字も引き継がない）
- 語句単位の標準辞書
- ギャル文字 → 通常文字への逆変換（曖昧性が高い。§14 D3）
- 中国語・韓国語の漢字への対応
- 手書き風レンダリング、画像出力

## 3. 中核となる設計判断

### 3.1 「結果」ではなく「構造 × スタイル」を保存する

v5 の漢字レイヤはこの一行に集約される。

```
v4:  信 → "ｲ言"                          （結果を保存。3,359 行を手書き）

v5:  信 → ⿰(亻, 言)                       構造テーブル（KanjiVG から生成）
     亻 → "ｲ"                            スタイルマップ（60〜70 件・手書き）
     ------------------------------------
     レンダラがビルド時に合成 → "ｲ言"
```

これにより:

- スタイル変更が全字に波及する（G1）
- 構造テーブルは外部データから生成できる（G2）
- 部品表記のゆれが原理的に発生しない（§1.3(b)）
- 再帰分解が自動で効く（§1.3(c)）

### 3.2 変換経路を 5 本に分ける

v4 の `kanji.json` には性質の異なる変換が混在していた。v5 では明示的に分け、
さらに **異体字置換**を新規に追加する。

| #   | 経路                             | 例                      | データ                    | 手書き           |
| --- | -------------------------------- | ----------------------- | ------------------------- | ---------------- |
| 1   | **例外**（筆画分解など）         | `川→丿丨丨` `水→ﾌＫ`    | `data/override.ts`        | ○ 新規設計       |
| 2   | **同形置換**                     | `上→㊤` `亜→亞` `丁→Ｔ` | `data/homoglyph.ts`       | ○ 新規設計       |
| 3   | **異体字置換**（新規）           | `学→學` `国→國` `沢→澤` | Unihan から生成           | ✕                |
| 4   | **構造分解**                     | `信→亻+言` → `ｲ言`      | KanjiVG から生成          | ✕                |
| 5   | **単体装飾**（新規）             | `口→ﾛ` `力→ｶ` `又→ﾇ`    | 部品スタイルを流用        | ✕                |
| —   | _部品スタイル_（3・4・5 に適用） | `亻→ｲ` `⺮→ｹｹ`          | `data/component-style.ts` | ○ 新規設計・拡充 |

経路 5 は前提 4 で解禁された新経路。v4 は部品スタイルを**分解の結果にしか適用しなかった**ため、
`口` `力` `又` `夕` のような 1 部品字は分解も置換もできず、必ず未変換だった。
同じスタイルマップを単体字にも適用するだけで、この穴が塞がる。

### 3.3 異体字置換を追加する理由

v4 では、上下構造の漢字（`学` `男` `花` `森` …1,409 字）が**一切変換されない**。
ギャル文字は本来「旧字体・異体字への置き換え」も多用するため、この層を足すと
分解できない字にも変換経路ができる。

```
v4:  学 → 学（変換されない）
v5:  学 → 學

v4:  沢 → ｼ尺
v5:  沢 → 澤 → ｼ睪    （異体字化してから分解する。§6.1）
```

データは Unicode の `Unihan_Variants.txt`（`kTraditionalVariant` / `kSemanticVariant` /
`kZVariant`）から生成する。**手書きデータは 1 行も増えない。**
ライセンスは Unicode License で、コピーレフトを持たない（§6.6）。

## 4. アーキテクチャ

### 4.1 全体パイプライン

```
入力 string
   │
   ▼
┌──────────────────────────────────────┐
│ 1. Segmenter                          │  コードポイント単位＋結合文字の保持
│    Array.from(str) ベース             │  （サロゲートペア安全）
└──────────────────────────────────────┘
   │  Segment[]
   ▼
┌──────────────────────────────────────┐
│ 2. Protector                          │  URL / 絵文字 / preserve 指定範囲
│                                       │  該当セグメントを sealed としてマーク
└──────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────┐
│ 3. Dictionary                         │  ユーザー定義ルール（あれば最優先）
└──────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────┐
│ 4. CharLayer（単一パス）               │  source から文字種を判定し
│    latin / digit / hiragana /         │  該当する表を 1 回だけ引く
│    katakana / symbol / kanji          │  ※レイヤ間カスケードなし
└──────────────────────────────────────┘
   │  ※ kanji のみ KanjiEngine（§6）に委譲
   ▼
出力 string
```

v4 にあった語句レイヤ（Aho–Corasick 等の多文字マッチ）は存在しない。
パイプラインは **1 セグメント = 1 変換**に単純化される。

### 4.2 カスケード汚染の解決

`E → ヨ → ∋` を防ぐための不変条件。

> **判定も変換も、常に `source`（元の入力文字）に対して行う。`output` は二度と読まない。**

```ts
interface Segment {
  /** 元の入力文字（1 書記素）。変換の判定材料は常にこちら */
  readonly source: string;
  /** 変換後の文字列。未変換なら source と同一 */
  output: string;
  /** true の場合、以降の処理は触れない */
  sealed: boolean;
}
```

```ts
// v4（誤り）: 6 つの表を直列に引く。前段の結果が後段の入力になる
if (alphabet[c]) c = alphabet[c];
if (kata[c]) c = kata[c]; // ← 汚染

// v5（正）: source から文字種を決め、該当する表だけを 1 回引く
const layer = classify(seg.source); // output は見ない
if (enabled[layer]) {
  seg.output = tables[layer].lookup(seg.source) ?? seg.source;
}
seg.sealed = true;
```

かな表を v4 のまま維持する以上、`ヨ`（カタカナ表のキー）と `E→ヨ`（英字表の値）の
衝突は避けられない。この不変条件がその唯一の防御線になる。

### 4.3 レイヤ定義

| ID         | 対象                     | 既定 | データ                           |
| ---------- | ------------------------ | ---- | -------------------------------- |
| `latin`    | `A-Za-z` `Ａ-Ｚａ-ｚ`    | on   | v4 の `alphabet.json` をそのまま |
| `digit`    | `0-9` `０-９`            | on   | v4 の `number.json` をそのまま   |
| `hiragana` | ひらがな                 | on   | v4 の `hiragana.json` をそのまま |
| `katakana` | カタカナ                 | on   | v4 の `katakana.json` をそのまま |
| `symbol`   | 記号・句読点             | on   | v4 の `other.json` をそのまま    |

## 5. データモデル

### 5.1 ソース形式の方針

| データ                               | 形式             | 理由                                         |
| ------------------------------------ | ---------------- | -------------------------------------------- |
| 構造・異体字テーブル（大・自動生成） | TSV              | 行指向で git diff が読める。スクリプトが吐く |
| スタイル/同形/例外（小・手書き）     | TypeScript       | 型チェックとコメントが付けられる             |
| かな・英数・記号                     | TypeScript       | v4 の JSON を機械変換して移植                |
| 配布成果物                           | 生成された `.ts` | 実行時にパースコストを持ち込まない           |

**原則: 手で書くファイルはすべて TypeScript。人間が読まないファイルだけ TSV。**

`scripts/port-v4-tables.ts` で JSON → TS へ機械変換する。値は 1 文字も変えない。

```ts
  あ: 'क॑',
  い: 'ﾚヽ',
  う: 'כֿ',
  // …
```

変換の正しさは移植テスト（§11）で全キー照合する。

### 5.3 構造テーブル（漢字）


| 演算子     | 意味          | v5 での扱い                                                          |
| ---------- | ------------- | -------------------------------------------------------------------- |
| `⿰`       | 左右 2 分割   | **常に展開する**（ギャル文字の基本形）                               |

| `⿴`〜`⿻` | 囲み・重ね    | `splitPolicy: "aggressive"` のときのみ展開                           |

## 6. 漢字エンジン

### 6.1 解決順序

漢字 1 文字に対し、次の順で経路を試し、最初に成功したものを採用する。

```
        ┌─────────────────────────────┐
 漢字 → │ 1. override（手書き例外）    │ → ヒットしたら確定
        └─────────────────────────────┘
                     │ miss
        ┌─────────────────────────────┐
        │ 2. homoglyph（同形置換）     │ → ヒットしたら確定
        └─────────────────────────────┘
                     │ miss
        ┌─────────────────────────────┐
        │ 3. variant（異体字化）       │ → 置換して次へ進む（確定しない）
        └─────────────────────────────┘
                     │
        ┌─────────────────────────────┐
        │ 4. decompose（構造分解）     │ → ヒットしたら確定
        └─────────────────────────────┘
                     │ miss（分解できない字）
        ┌─────────────────────────────┐
        │ 5. style（単体装飾）         │ → miss なら 3 の結果を返す
        └─────────────────────────────┘
```

**3 は「確定」ではなく「置換して次へ進む」点が重要**で、これにより異体字化と分解が合成される。

```
沢 → variant → 澤 → decompose(澤) = ⿰氵睪 → ｼ睪
学 → variant → 學 → decompose(學) = ⿱… → 分割不可 → 學 を返す
信 → variant なし → decompose(信) = ⿰亻言 → ｲ言
男 → variant なし → decompose(男) = ⿱田力 → 両パーツとも読める → 田ｶ   ← v5 で新規
口 → variant なし → decompose 不可 → style(口) → ﾛ                    ← v5 で新規
```

```ts
function convertKanji(ch: string, ctx: Context): string {
  // 1. 例外
  const ov = ctx.override[ch];
  if (ov) return ctx.pick(ov);

  // 2. 同形置換
  const hg = ctx.homoglyph[ch];
  if (hg) return ctx.pick(hg);

  // 3. 異体字化（確定しない。以降は base に対して処理する）
  const base = ctx.enableVariant ? (ctx.variant.get(ch) ?? ch) : ch;

  // 4. 構造分解
  const decomposed = decompose(base, 0, ctx);
  if (decomposed) return decomposed;

  // 5. 単体装飾（分解できない 1 部品字を救う）
  return styleOf(base, 'any', ctx) ?? base;
}
```

経路 4 と経路 5 が同じ `styleOf()` / `componentStyle` を共有している点が §3.2 で述べた要点。

### 6.2 分解アルゴリズム

```ts
function decompose(char: string, depth: number, ctx: Context): string | null {
  if (depth > ctx.maxDepth) return null;

  const ids = ctx.structure.get(char);
  if (!ids) return null;
  if (!isLinearizable(ids.operator, depth, ctx)) return null;

  const parts: string[] = [];
  for (const [i, arg] of ids.operands.entries()) {
    const position = positionOf(ids.operator, i); // "left" | "right" | "any"
    const sub = shouldRecurse(arg, ctx) ? decompose(arg, depth + 1, ctx) : null;
    parts.push(sub ?? styleOf(arg, position, ctx) ?? arg);
  }
  return parts.join('');
}

function styleOf(component: string, pos: Position, ctx: Context): string | null {
  const c = normalizeComponent(component, pos, ctx);
  const s = ctx.componentStyle[`${c}@${pos}`] ?? ctx.componentStyle[c];
  return s ? ctx.pick(s) : null;
}
```

**v4 データによる妥当性確認**

前提 4 により v4 との一致は**要求されない**。以下は「このアルゴリズムが人手による判断を
再現できるか」を確かめるための検証であり、拘束条件ではない。

| 字   | 構造                  | v5 の導出          | v4 の値 |                                |
| ---- | --------------------- | ------------------ | ------- | ------------------------------ |
| `信` | `⿰亻言`              | `ｲ言`              | `ｲ言`   | 一致                           |
| `例` | `⿰亻列`, `列=⿰歹刂` | `ｲ歹ﾘ`             | `ｲ歹ﾘ`  | 一致                           |
| `倒` | `⿰亻到`, `到=⿰至刂` | `ｲ至ﾘ`             | `ｲ至ﾘ`  | 一致                           |
| `傾` | `⿰亻頃`, `頃=⿰匕頁` | `ｲﾋ頁`             | `ｲﾋ頁`  | 一致                           |
| `倍` | `⿰亻咅`, `咅=⿱立口` | `ｲ立ﾛ`             | `ｲ立ﾛ`  | 一致                           |
| `語` | `⿰言吾`, `吾=⿱五口` | `言吾`（再帰せず） | `言吾`  | 一致                           |
| `部` | `⿰咅阝`, `咅=⿱立口` | `立ﾛ⻏`            | `立ﾛ卩` | **v4 の誤りを修正**（§1.3(b)） |
| `男` | `⿱田力`              | `田ｶ`              | 未変換  | **意図的に改善**（§6.3.1）     |
| `口` | 分解不可              | `ﾛ`                | 未変換  | **意図的に改善**（経路 5）     |

上位 6 行が一致することで、§6.3 の 2 規則（トップレベルは横並び優先／読めない部品だけ再帰）が
人手の判断を機械的に再現できていることが確認できる。下位 3 行は前提 4 で解禁した改善分。

### 6.3 構造フィルタ ― なぜ `倍` は展開して `語` は展開しないのか

`倍→ｲ立ﾛ`（`咅=⿱立口` を展開）と `語→言吾`（`吾=⿱五口` を展開しない）は
一見矛盾するが、v4 データを精査すると明確な基準がある。

> **`吾` は単独で読める字だが、`咅` は読めない。**

`吾` は JIS X 0208 に収録された見慣れた字なので、そのまま置いたほうがギャル文字として自然。
`咅` は JIS X 0208 に無く、置いても読めないので分解される。これを機械化する。

```ts
/** 再帰するかどうか＝その部品が「そのまま置いて読めるか」 */
function shouldRecurse(component: string, ctx: Context): boolean {
  if (ctx.componentStyle[component]) return false; // スタイル定義済み → それを使う
  if (ctx.legibleSet.has(component)) return false; // 読める字 → そのまま置く
  return true; // 読めない字 → 分解を試みる
}
```

`legibleSet` の既定は **JIS X 0208（第1・第2水準）**。

#### 6.3.1 分割方針（`splitPolicy`）― 前提 4 で解禁される最大の変更

v4 はトップレベルで `⿰`（左右）しか分割しなかった。このため
**上下構造の漢字 1,409 字が一切変換されない**という大穴があった。

```
v4:  男 → 男（未変換）   早 → 早（未変換）   花 → 花（未変換）
```

前提 4 により、この方針自体を変更できる。3 段階の方針を用意し、既定を `"balanced"` とする。

| `splitPolicy`            | `⿰` `⿲` | `⿱` `⿳`                          | `⿴`〜`⿻`      | 想定            |
| ------------------------ | --------- | ---------------------------------- | --------------- | --------------- |
| `"horizontal"`           | ○         | ネストのみ                         | ✕               | v4 相当。保守的 |
| **`"balanced"`（既定）** | ○         | **全パーツが読める/装飾済みなら○** | ✕               | 推奨            |
| `"aggressive"`           | ○         | ○                                  | ○（順に並べる） | 最大網羅        |

`"balanced"` の判定:

```ts
function canSplitVertical(ids: Ids, ctx: Context): boolean {
  // 上下分割は「並べたときに両方読める」ときだけ許す。
  // 男 = ⿱田力 → 田 も 力 も読める     → 田ｶ      ○
  // 花 = ⿱艹化 → 艹 は装飾済み(ﾅﾅ)     → ﾅﾅ化     ○
  // 責 = ⿱龶貝 → 龶 が読めず装飾も無い → 分割しない ✕
  return ids.operands.every((c) => ctx.legibleSet.has(c) || ctx.componentStyle[c] !== undefined);
}
```

この 1 つの条件で、v4 が捨てていた上下構造字の大半に経路ができる。
**部品スタイルの拡充（§5.5）と相乗する**点が重要で、`艹→ﾅﾅ` を 1 行足すと
`艹` を含む上下構造字がまとめて分割可能になる。

構造フィルタ本体:

```ts
function isLinearizable(ids: Ids, depth: number, ctx: Context): boolean {
  switch (ids.operator) {
    case '⿰':
    case '⿲': // 左右・左中右
      return true;

    case '⿱':
    case '⿳': // 上下
      if (depth >= 1) return true; // ネストは常に許可（咅→立ﾛ）
      switch (ctx.splitPolicy) {
        case 'horizontal':
          return false;
        case 'balanced':
          return canSplitVertical(ids, ctx);
        case 'aggressive':
          return true;
      }

    default: // 囲み・重ね
      return ctx.splitPolicy === 'aggressive'; // 国→囗玉, 回→囗ﾛ
  }
}
```

#### 6.3.2 なぜ「ネストは常に許可」なのか

`depth >= 1` で無条件に許可しているのは、ネストした位置に現れる部品は
**すでに一度分解された文脈にあり、読み手が分解を期待している**ため。
§6.3 の `倍→ｲ立ﾛ`（`咅=⿱立口` を展開）が v4 の人手判断でもそうなっていたことが裏付けになる。

### 6.4 異体字テーブルの生成規則

`Unihan_Variants.txt` から次の優先順で 1 対 1 のマップを作る。

| 優先 | フィールド            | 意図                                       |
| ---- | --------------------- | ------------------------------------------ |
| 1    | `kTraditionalVariant` | 新字体 → 旧字体（`学→學` `国→國` `沢→澤`） |
| 2    | `kZVariant`           | 字形の異体（意味・読みは同一）             |
| 3    | `kSemanticVariant`    | 意味が同一の異体字                         |

除外規則:

- 変換先が変換元と同一のもの
- 変換先が BMP 外（フォント欠落が多く読めない）
- **変換先の方が画数が少ないもの**（`kSimplifiedVariant` は使わない。ギャル文字は
  「難しく見せる」方向なので、簡体字化は逆効果）
- 複数候補がある場合は Unihan の記載順で先頭を採用し、`data/variant-override.ts` で個別に上書き可能

生成後、**目視レビュー用の HTML を出力する**（`scripts/review-variants.ts`）。
数千件を全数チェックするのは非現実的なため、常用漢字 2,136 字ぶんだけ先に確認し、
残りは問題報告ベースで `variant-override.ts` に積む運用とする。

### 6.5 部品の正規化と位置依存

外部データは同じ部品を異なるコードポイントで表現することがある。
（`亻` U+4EBB / `人` U+4EBA、`氵` U+6C35 / `水` U+6C34、`⺅` U+2E85）

```ts
// data/component-normalize.ts
export const componentAlias: Record<string, string> = {
  '⺅': '亻',
  '⺡': '氵',
  '⺘': '扌',
  // IDS の第1オペランド（left）に限り適用するもの
  '人@left': '亻',
  '水@left': '氵',
  '手@left': '扌',
};
```

**`阝` の位置依存問題**: `阝`(U+961D) は左（阜・こざとへん `⻖`）と右（邑・おおざと `⻏`）で
字形が異なるが、Unicode 上は同一コードポイント。スタイルマップのキーを
`部品@位置` にすることで解決する（§5.5）。

解決順序: `部品@位置` → `部品` → 正規化後に再試行 → 素通し。

Unicode の `CJKRadicals.txt`（Unicode License）は康熙部首と CJK 統合漢字の対応を
与えるため、`⺅→人` のような別形対応の生成に利用できる。

| 構造（IDS） | CHISE IDS / cjkvi-ids   | 約 90,000 | **GPLv2**           | **不採用** |
| 異体字      | **Unihan_Variants.txt** | 全字      | **Unicode License** | **採用**   |
| 部首対応    | **CJKRadicals.txt**     | —         | Unicode License     | 採用       |

調査結果:

- **Unicode UCD に `IDS.txt` は存在しない。** 最新 UCD のファイル一覧を確認したが、
  IDS を含むファイルは無い。`USourceData.txt` は未エンコード U-source 文字の IDS のみで対象外。
  記述文字 U+2FFC–U+2FFF 自体は Unicode 15.1 で追加されているが、データは提供されない。
- **cjkvi-ids の `ids.txt` は CHISE 由来で GPLv2。** README に
  「'ids.txt' is derived from CHISE project. License follows their terms.」と明記。
  ISC ライセンスの本パッケージに取り込むと**成果物まで GPL 汚染される**ため不採用。
- **KanjiVG は CC BY-SA 3.0。** 各 SVG に `kvg:element`（部品）と
  `kvg:position="left"|"right"` が付いており、**位置情報つきの分解が直接得られる**。
  §6.5 の位置依存問題に直接効くため、IDS を解釈するより本用途に適している。
- **Unihan は Unicode License。** 帰属表示のみでコピーレフトを持たないため、
  異体字テーブルはライセンス上の制約がほぼ無い。

#### ライセンス戦略

```
galjp（コード）                    … ISC
  ├─ src/generated/structure.ts    … KanjiVG 由来 → CC BY-SA 3.0
  └─ src/generated/variant.ts      … Unihan 由来  → Unicode License
```

CC BY-SA は「派生データに同ライセンスを要求する」が、**コードには伝播しない**
（GPL と異なりリンクによる汚染が無い）。よって:

1. 生成データファイルの先頭に帰属表示コメントを入れる。
2. `NOTICE` に KanjiVG（© Ulrich Apel, CC BY-SA 3.0）と Unicode を明記。
3. `package.json` の `license` は `ISC`、`LICENSE-KanjiVG` / `LICENSE-Unicode` を別途同梱。

より厳格に分離したい場合は §14 D1 を参照。

## 7. ビルドパイプライン

### 7.1 全体

```
KanjiVG (SVG)         → scripts/extract-structure.ts → data/structure.tsv
Unihan_Variants.txt   → scripts/extract-variant.ts   → data/variant.tsv
JIS X 0208            → scripts/build-legible.ts     → data/legible.tsv
v4 の lib/chars/*.json→ scripts/port-v4-tables.ts    → data/{hiragana,katakana,latin,digit,symbol}.ts
                                    │
data/component-style.ts ────────────┤
data/component-normalize.ts ────────┤
data/homoglyph.ts       ────────────┤
data/override.ts        ────────────┤
data/variant-override.ts────────────┤
                                    ▼
                        scripts/build-tables.ts   ← §6 のエンジンを実行
                                    │
                                    ▼
                        src/generated/kanji.ts   （事前計算済みテーブル）
                        src/generated/meta.ts    （収録数・ハッシュ・ソース情報）
```

**事前計算を既定とする理由**: 実行時に IDS を解釈するとデータ（数 MB）を同梱することになり、
ブラウザ用途で成立しない。ビルド時に潰しておけば、実行時は単なる辞書引きで済む。

`port-v4-tables.ts` は 1 回だけ実行して結果をコミットする（v4 のファイルは削除する）。

### 7.2 出力形式

生成物はプレーンな文字列 2 本 + 遅延構築される `Map`。

```ts
// src/generated/kanji.ts （自動生成・編集禁止）
// Derived from KanjiVG (c) Ulrich Apel, CC BY-SA 3.0
// Derived from Unicode Character Database, (c) Unicode, Inc.

/** キー: コードポイント昇順に連結 */
export const KEYS = '一丁七万丈三上下…';

/** 値: KEYS と同じ順序。U+0000 区切り */
export const VALUES = '…';

let table: Map<string, string> | null = null;
export function lookup(ch: string): string | undefined {
  table ??= build(); // 初回参照時のみ構築
  return table.get(ch);
}
```

**サイズ方針**: 現状 87KB(JSON) / 3,359 字 → 目標 60KB 未満（raw）/ 20KB 未満（gzip）で
8,000 字以上。ただし gzip 後の差は小さいため、**バイト数の最適化より可読性と正しさを優先する**。
凝った可変長エンコーディングは、サイズ計測で必要性が示された場合にのみ導入する
（`scripts/size-check.ts` を CI に入れ、予算超過で失敗させる）。

### 7.3 品質ゲート

v4 との出力一致は**漢字については一切要求しない**（前提 1・4）。代わりに次を CI で強制する。

| ゲート             | 内容                                                       | 閾値                       |
| ------------------ | ---------------------------------------------------------- | -------------------------- |
| **かな移植**       | かな・英数・記号の全キーが v4 と 1 文字も違わない          | 完全一致必須               |
| **一貫性**         | 同一部品が複数表記になっていない（§1.3(b) の再発防止）     | 違反 0                     |
| **デッドエントリ** | `componentStyle` / `override` の全キーが実際に使われている | 違反 0                     |
| **カバレッジ**     | 常用漢字のうち変換できる割合                               | ≥ 70%（実測 73.2%・§15.3） |
| **カバレッジ**     | JIS X 0208 のうち変換できる割合                            | ≥ 75%（実測 77.7%・§15.3） |
| **非退行**         | 変換率が前リリースを下回らない                             | 低下で失敗                 |
| **サイズ**         | §10.1 の予算                                               | 超過で失敗                 |

閾値は実測（§15.1）に基づいて確定済み。

**v4 との差分**は CI ゲートにしない。フェーズ 5 で 1 回だけ `scripts/compare-v4.ts` を
手動実行し、`v4 のみ変換できる` に該当する字を目視レビューする。
これは**劣化の検出**ではなく、**`override.ts` に入れる価値のある人手の工夫を拾い上げる**
ための作業（例: `川→丿丨丨` のような筆画分解はアルゴリズムでは出せない）。
レビュー後、このスクリプトと v4 データは削除する。

## 8. ランタイム API

### 8.1 基本

```ts
import { galjp } from 'galjp';

galjp('信頼してる'); // "ｲ言束頁Ｕτゑ"
galjp('Hello World!'); // "丩ヨ└└口 山口尺└囙.ᐟ"
galjp('学校'); // "學木交"    ← v4: "学木交"（学が未変換だった）
galjp('男女'); // "田ｶ女"     ← v4: "男女"（上下分割しなかった）
galjp(''); // ""

// 分割方針を v4 相当まで絞る
galjp('男女', { splitPolicy: 'horizontal' }); // "男女"
```

### 8.2 オプション

```ts
export interface GaljpOptions {
  /** レイヤの有効/無効。既定は全て true */
  layers?: Partial<Record<LayerId, boolean>>;

  /** 異体字置換（学→學）を行うか。既定 true */
  variant?: boolean;

  /** 漢字の分割方針。既定 "balanced"（§6.3.1）
   *  "horizontal" = 左右分割のみ / "balanced" = 読める上下分割も許可
   *  "aggressive" = 囲み構造まで展開 */
  splitPolicy?: 'horizontal' | 'balanced' | 'aggressive';

  /** 分解できない 1 部品字を装飾するか（口→ﾛ）。既定 true */
  styleStandalone?: boolean;

  /** 漢字分解の最大再帰深度。既定 2 */
  maxDepth?: number;

  /** 乱数シード。未指定なら決定的（各候補の先頭を採用） */
  seed?: number | string;

  /** 変換しない範囲。既定は URL と絵文字を保護 */
  preserve?: RegExp | readonly RegExp[] | ((text: string) => boolean) | false;

  /** ユーザー定義ルール（最優先・複数文字可）。標準辞書は同梱しない */
  dictionary?: Readonly<Record<string, string | readonly string[]>>;
}

export type LayerId = 'latin' | 'digit' | 'hiragana' | 'katakana' | 'kanji' | 'symbol';
```

`dictionary` は §1.4 で廃止した語句レイヤの代替。**キーは正規表現として解釈せず、
リテラル文字列として最長一致**で処理する。出力は即座に sealed となり再変換されない。

```ts
galjp('まじ卍', { dictionary: { まじ: 'маＵ”' } });
```

### 8.3 再利用可能なコンバータ

オプション解決とテーブル構築を 1 度だけ行うための API。

```ts
import { createConverter } from 'galjp';

const conv = createConverter({ variant: false, seed: 42 });
for (const line of lines) console.log(conv.convert(line));
```

```ts
export interface Converter {
  convert(input: string): string;
  /** 1 文字の変換候補をすべて返す（デバッグ・UI 用） */
  candidates(char: string): readonly string[];
  /** どの経路で変換されたかを返す（デバッグ用） */
  explain(char: string): {
    route: 'override' | 'homoglyph' | 'variant' | 'decompose' | 'style' | 'none';
    result: string;
    steps: readonly string[];
  };
  readonly options: Required<GaljpOptions>;
}
```

`explain()` は §6.1 の 5 経路のどれが効いたかを返す。データの不具合報告を
再現しやすくするための開発者向け API。

### 8.4 エラー方針

| 入力                            | 挙動                                      |
| ------------------------------- | ----------------------------------------- |
| `""`                            | `""` を返す                               |
| `null` / `undefined` / 非文字列 | `TypeError`                               |
| 不正な `options`                | `TypeError`（メッセージにキー名と期待型） |

検証は手書きの `if` 列ではなく、単一のスキーマ定義から生成する。

## 10. パフォーマンス設計

### 10.1 目標

| 指標                                        | 目標値                         |
| ------------------------------------------- | ------------------------------ |
| 初回 `galjp()` 呼び出し（テーブル構築含む） | < 5 ms                         |
| 2 回目以降・1,000 文字                      | < 1 ms                         |
| バンドルサイズ（gzip, 全レイヤ）            | < 45 KB（実測 40.1 KB・§15.4） |
| バンドルサイズ（gzip, kanji レイヤ除外時）  | < 3 KB                         |

### 10.2 手法

- **遅延構築**: 漢字テーブルの `Map` は最初の漢字入力時にのみ構築する。
  英数のみの入力ではテーブル構築が一切走らない。
- **Tree-shaking**: 各レイヤを個別モジュールに分け、漢字テーブルを落とせる構成にする。
- **多文字マッチの排除**: 語句レイヤを廃止したため、`dictionary` 未指定時は
  **1 セグメント 1 ルックアップの単純ループ**で済む。Aho–Corasick 等は不要。
  `dictionary` 指定時のみ最長一致トライを構築する。
- **正規表現の排除**: 文字種判定はコードポイント範囲比較で行う。

## 11. テスト戦略

| 種別           | 内容                                                                 | ツール                         |
| -------------- | -------------------------------------------------------------------- | ------------------------------ |
| **かな移植**   | v4 の 4 表の全キーで出力が 1 文字も変わらない（G6）                  | Vitest + v4 JSON を fixture 化 |

| デッドエントリ | `componentStyle` / `override` の未使用キー検出                       | ビルド時アサート               |
| カバレッジ     | §7.3 の閾値                                                          | Vitest                         |
| カスケード     | `E`→`ヨ`（`∋` にならない）、`ヨ`→`∋` の両立                          | Vitest                         |
| プロパティ     | 任意の Unicode 文字列で例外を出さない・書記素を壊さない              | fast-check                     |
| サロゲート     | BMP 外文字・絵文字・結合文字を含む入力                               | Vitest                         |

### 15.2 設計からの変更点

| #      | 変更                                                           | 理由                                                                                                                                                                                                                                                                                                                                   |
| ------ | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C1** | **§7.2 の事前計算をやめ、実行時にエンジンを動かす**            | 設計は「実行時に IDS を解釈するとデータが数 MB になる」ことを理由に事前計算としていたが、これは**生の KanjiVG（12.9 MB）を同梱した場合**の話だった。抽出後の構造テーブルは 5,129 件・20,600 字しかなく、同梱しても事前計算版と大差ない。実行時エンジンなら `splitPolicy` `variant` `maxDepth` が全部そのまま効くため、こちらを採用した |
| **C2** | **再帰条件に「部品自体が横に割れるなら再帰」を追加**（§6.3）   | 設計の「読めない部品だけ再帰」だけでは `例→ｲ列`（v4 は `ｲ歹ﾘ`）になった。v4 データ 3,286 字で 3 案を比較し、`読めない ∨ 部品が横割れ` が **95.9% 一致**（読めるかどうかのみは 92.4%）で最良と確認して採用                                                                                                                              |
| **C3** | **`renderable` を `legible` から分離**（`data/renderable.ts`） | 上下分割の可否判定に JIS X 0208 を使うと `疒` `灬` `罒` が弾かれ、`病` `熱` `置` が変換できなかった。これらは JIS X 0208 の**漢字ではない**が日本語フォントでは確実に描画される。判定を「読める字か」と「描画できるか」に分けた。常用漢字の変換率が 70.9% → 73.2% に改善                                                               |
| **C4** | **`⿺`（繞）を無条件分割、`⿸`（垂）を条件付き分割に分類**     | v4 が `建→廴聿` `巡→ぇ巛` のように繞を展開していたため。垂（`广` `疒`）は v4 が展開しておらず、balanced の可読性判定に委ねた                                                                                                                                                                                                           |
| **C5** | `legible` セットを**部品として出現しうる字に限定**             | エンジンは部品しか照会しないため無損失。19 KB → 3.5 KB                                                                                                                                                                                                                                                                                 |
| **C6** | `悪→惡` を homoglyph から除外                                  | 利用者判断。分解経路に回り `悪 → 亜心` になる                                                                                                                                                                                                                                                                                          |

### 15.3 変換率が目標に届かなかった理由

常用漢字 2,140 字のうち未変換 574 字の内訳:

| 要因                   | 件数   | 説明                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 構造データなし         | 約 525 | うち約 150 は本当に 1 部品の字（`一` `七` `丈` `不` …）で、分解のしようがない。残りは **KanjiVG が部品に名前を付けていない**ケース（`低` `侯` `修` `倉` など、右側が未エンコード字形）。KanjiVG の左右分割 3,870 件のうち 375 件がこれに該当し、`CDP-8BC4` のようなプレースホルダか入れ子 IDS が入っている |
| 上下分割を可読性で却下 | 75     | `光` `共` `券` など、上または下が描画できない部品                                                                                                                                                                                                                                                          |
| 垂を却下               | 20     |                                                                                                                                                                                                                                                                                                            |

**設計時の 95% / 90% という目標は、KanjiVG の網羅性を確認せずに立てた見込み値であり、根拠が無かった。**
実測に合わせて §7.3 のゲートを 70% / 75% に改め、非退行ゲート（前リリースを下回らない）で守る方針に変更した。

改善の余地（未実施）:

- `⺌` `龶` `𠆢` など上下分割を阻んでいる部品を `renderable.ts` / `component-style.ts` に追加する（1 行ずつ）
- KanjiVG が落とした 375 字を別の IDS ソースで補完する（ただし GPL 問題があるため §6.6 の判断を再検討する必要がある）

### 15.4 バンドルサイズ

`dist/index.js` は **86.1 KB raw / 40.1 KB gzip**（目標 25 KB gzip）。内訳は構造テーブル 62 KB、
かな・英数表と実装コード約 20 KB、legible 3.5 KB、異体字 0.5 KB。

実装中に 2 段階削減した:

1. **esbuild の `charset` を `utf8` に変更** — 既定の `ascii` は CJK を `\uXXXX`（6 バイト）に展開しており、
   これだけで 182 KB → 101 KB になった。`tsup` のトップレベル `charset` は無効で、
   `esbuildOptions` 経由でないと効かない
2. **`legible` の限定**（C5）— 101 KB → 86.1 KB

これ以上は構造テーブル本体の圧縮（部品を ASCII インデックス化するなど）が必要だが、
gzip が既に重複を吸収しており費用対効果が低い。**目標値のほうを実測に合わせて 45 KB gzip に改める。**
